# Resilience Evidence

This document satisfies **§20 Resilience Demonstration** of the hackathon
brief:

> *Evidence of how the app responds to at least one meaningful failure.*

It covers all **5 injectable simulator faults** (`unavailable`,
`error_rate`, `latency`, `stale_data`, `stream_disconnect`) defined in
[`docs/simulator_integration_guide.md`](./simulator_integration_guide.md) §8
and called out in the brief §13.

A reproducible tour script lives at [`../loadtest/fault-tour.py`](../loadtest/fault-tour.py)
and the raw per-fault snapshots are saved as
[`../loadtest/fault-tour.json`](../loadtest/fault-tour.json).

---

## 1. Failure-handling mechanisms

| Mechanism | File | What it does |
|---|---|---|
| **Last-known-good cache** (`CACHE`) | `api/app/simulator/client.py` | Per-endpoint response cache with 3 s TTL. On 503 / connection error / timeout, returns the cached value so read endpoints stay responsive. |
| **Circuit breaker** (`CB`) | `api/app/simulator/client.py` | Opens after 5 consecutive failures. After 30 s cooldown, the next call is allowed through (half-open); a success closes it. |
| **Stale-data detection** (`LAST_STALE`) | `api/app/simulator/client.py` | Reads `X-Simulator-Stale: true` from any `/v1/*` response and propagates it to `STORE.stale` and the `fuelops_simulator_stale` gauge. |
| **SSE auto-reconnect** (`SSEConsumer`) | `api/app/simulator/sse.py` | Exponential backoff 1 s → 30 s; resets on successful connect; REST re-fetch on every tick. |
| **Safety-net poll** | `api/app/ingest.py` | Every 3 s, the ingest loop re-fetches state and updates gauges even when SSE has silently dropped. |
| **Fallback decision policy** | `api/app/policy.py` | A second, simpler policy (`threshold-v1`) is always available; the system-status page reports which one is active. |
| **Operator visibility** | `/api/system/status`, `/status` page | `fallback_active`, `stale`, recent `SystemEvent` rows, and per-service health. |

## 2. Failure-mode matrix

| Fault | Where injected | API behavior | UI behavior | Recovery |
|---|---|---|---|---|
| `unavailable` | `POST /api/admin/demo/faults {"type":"unavailable"}` | CB opens after 5 × 503. Reads served from `CACHE`. `/api/overview` keeps returning 200. | "Fallback active" banner appears. Status page marks simulator `Healthy` (because `/v1/health` bypasses faults) and shows `fallback_active: true`. | `POST /admin/faults/clear` removes the fault. The next cache miss calls the simulator; a 200 closes the CB on the next `before()` check. |
| `error_rate` | `POST /api/admin/demo/faults {"type":"error_rate","parameters":{"rate":0.3}}` | Same as unavailable — random 503s trip the CB; reads fall through to cached values. | "Fallback active" banner. | Same. |
| `latency` | `POST /api/admin/demo/faults {"type":"latency","parameters":{"delay_ms":500}}` | Each call sleeps 500 ms before returning. Reads succeed but slower. CB does not open (no failures). | "Fallback active" banner is **not** shown. Latency is visible in Grafana (panel #6) and Prometheus (`fuelops_simulator_request_duration_seconds`). | Fault auto-expires after `duration_seconds`. |
| `stale_data` | `POST /api/admin/demo/faults {"type":"stale_data"}` | Simulator returns 200 + `X-Simulator-Stale: true`. The client sets `LAST_STALE = True`; the next ingest poll sets `STORE.stale = True` and `fuelops_simulator_stale = 1`. | "Fallback active" banner appears. Topbar simulator pill flips from **LIVE** to **STALE DATA**. | `POST /admin/faults/clear`. Next ingest poll re-fetches without the header; `STORE.stale` flips back to `false` within 3–8 s. |
| `stream_disconnect` | `POST /api/admin/demo/faults {"type":"stream_disconnect"}` | `GET /v1/stream` returns 503. The SSE consumer's exponential backoff kicks in (1 s → 30 s). The safety-net REST poll keeps the store warm. The `fuelops_sse_connected` gauge drops to 0; the `fuelops_snapshot_age_ticks` gauge grows; the next reconnect resets both. | Status page shows "SSE stream" with the gauge state. The store keeps serving cached data; the UI keeps working. | Fault auto-expires. The SSE consumer reconnects on the next backoff tick. |

## 3. Captured trace

Generated by `python3 loadtest/fault-tour.py` against a fresh API container.
Each fault is injected for 25 s; the snapshot is taken 8 s after injection.
The 5th fault (`stale_data`) is run last, after a 35 s wait to let the
circuit-breaker cooldown fully reset.

| Fault | `overall` | `fallback_active` | `stale` | SSE | `/api/overview` |
|---|---|---|---|---|---|
| (baseline, no fault) | `Healthy` | `false` | `false` | Connected | 200 |
| `unavailable`        | `Healthy` | `true`  | `false` | Connected | 200 |
| `error_rate`         | `Healthy` | `true`  | `false` | Connected | 200 |
| `latency`            | `Healthy` | `false` | `false` | Connected | 200 (slower) |
| `stream_disconnect`  | `Healthy` | `false` | `false` | Connected † | 200 |
| `stale_data`         | `Healthy` | `true`  | **`true`** | Connected | 200 |

† The SSE consumer briefly disconnects; the snapshot is taken after the
reconnect window. The `fuelops_sse_connected` gauge drops to 0 during the
fault and rises back to 1 once SSE reconnects.

Each row's full JSON snapshot is in
[`loadtest/fault-tour.json`](../loadtest/fault-tour.json).

### Prometheus evidence

```bash
# Circuit breaker state during / after unavailable fault:
$ curl -s 'http://localhost:9090/api/v1/query?query=fuelops_circuit_breaker_state'
{"data":{"result":[{"value":[...,"1"]}]}}   # during fault → open
{"data":{"result":[{"value":[...,"0"]}]}}   # after clear → closed

# Stale-data gauge after stale_data injection:
$ curl -s 'http://localhost:9090/api/v1/query?query=fuelops_simulator_stale'
{"data":{"result":[{"value":[...,"1"]}]}}   # during fault → stale
{"data":{"result":[{"value":[...,"0"]}]}}   # after clear → fresh

# Simulator call outcomes (the `outcome` label splits ok vs fault_injected):

# {outcome="ok", endpoint="stations"}            → growing under normal traffic
# {outcome="fault_injected", endpoint="..."}     → growing under unavailable / error_rate

# SSE connection state:
$ curl -s 'http://localhost:9090/api/v1/query?query=fuelops_sse_connected'
# 0 during stream_disconnect, 1 after reconnect
```

## 4. Demo recipe (≈ 3 minutes)

Run this during the judged demo to satisfy §20 #9 in front of the
reviewers.

```bash
# 0. Pre-conditions: stack up, simulator RUNNING, /status page open in a tab.
make up
open http://localhost:3000/status   # System status page

# 1. Inject each fault in turn (UI buttons on /demo do the same):
TOKEN=local-dev-token

curl -s -X POST http://localhost:8080/api/admin/demo/faults \
  -H "X-Operator-Token: $TOKEN" -H 'Content-Type: application/json' \
  -d '{"type":"unavailable","duration_seconds":20}'
# → after 8s: status shows fallback_active=true, simulator still Healthy
# → Prometheus circuit_breaker_state = 1

curl -s -X POST http://localhost:8080/api/admin/demo/faults/clear \
  -H "X-Operator-Token: $TOKEN"
# → after 8s: fallback_active=false, circuit_breaker_state = 0

# Repeat for error_rate, latency, stream_disconnect.

# 2. Stale-data demo — wait 35s for CB cooldown before this step:
sleep 35
curl -s -X POST http://localhost:8080/api/admin/demo/faults \
  -H "X-Operator-Token: $TOKEN" -H 'Content-Type: application/json' \
  -d '{"type":"stale_data","duration_seconds":30}'
# → after 8s: topbar pill flips to "STALE DATA"; fuelops_simulator_stale = 1
# → operators know the snapshot is out-of-date

curl -s -X POST http://localhost:8080/api/admin/demo/faults/clear \
  -H "X-Operator-Token: $TOKEN"
# → after 8s: pill back to "LIVE"
```

For a fully automated tour: `python3 loadtest/fault-tour.py`.

## 5. §20 deliverable #9 statement of compliance

The platform handles **all five** simulator-dependency failure modes
defined in the simulator integration guide. For each:

- The API continues serving operator reads (`/api/overview`, `/api/alerts`,
  `/api/recommendations`, `/api/system/status`) from cached state when
  the simulator is unavailable or returning errors.
- The UI surfaces the degraded state through:
  - the system status page (`fallback_active`, `stale`, per-service health)
  - the topbar simulator pill (LIVE / STALE DATA)
  - the degraded banner on `/`, `/recommendations`, `/alerts` when
    `fallback_active` is true.
- The Prometheus metrics layer records the circuit-breaker state, stale
  state, simulator-call outcomes, and SSE connection state. Grafana
  panels "freshness + resilience" and "fallback activations" make this
  observable in real time.
- All faults can be cleared with a single `POST /api/admin/demo/faults/clear`
  call (gated by `X-Operator-Token`); recovery is automatic — no operator
  intervention needed.

This satisfies §13 ("define what happens when something goes wrong") and
§20 #9 ("evidence of how the app responds to at least one meaningful
failure").
